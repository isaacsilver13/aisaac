# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A standalone links-and-health dashboard for Isaac's other applications. `backend/` is a FastAPI monitor with a normalized health contract; `frontend/` is a React dashboard. The monitor only checks configured *public* endpoints server-side — it never accesses another app's database, local artifacts, authenticated data, or financial data. **One narrow exception:** Claude usage and Neon/Fly cost figures are *pushed* by external jobs to `POST /internal/metrics/{source}` (`claude`, `neon`, `fly`; guarded by `INTERNAL_REPORT_SECRET`, stored by `metrics_store.py`) and served from `GET /api/v1/command-center/financials`, which requires `DASHBOARD_READ_TOKEN` (a separate read-only token sent as `X-Dashboard-Token`). **A second narrow exception:** the Obsidian second-brain vault (`wikis/`, `knowledge/`, `projects/`, `questions/` only) is pushed by `scripts/second_brain_push.py` to `POST /internal/second-brain/sync` (same `INTERNAL_REPORT_SECRET`; refuses to push if a note looks like it holds a secret), stored by `second_brain_store.py` at `SECOND_BRAIN_DB_PATH` (`/data` in prod), and read back only through `GET /api/v1/second-brain/*` behind `DASHBOARD_READ_TOKEN`; reads are key lookups and never touch the filesystem. Wikilinks are resolved once, at sync time, into a `links` table (plus a per-note `link_map`), which backs backlinks, `/second-brain/portals` and `/second-brain/graph`; the frontend renders them as a Wikipedia-style article/portal viewer at `/knowledge/*`. `/learning` serves one daily module from the same notes (`learning.py`: fixed rotation over knowledge/ + wikis/ by America/Chicago date; questions/exercises are generated deterministically from note structure, no LLM) via `GET /api/v1/learning/module` (read token); `POST /api/v1/learning/progress` (write token) records completion in a `learning_progress` table that sync never clears. **A third narrow exception:** `GET /api/v1/apps/{id}/deployments` (behind `DASHBOARD_READ_TOKEN`) pulls release history for an app's `fly_app` using a read-only `FLY_API_TOKEN` (`fly_client.py`, cached 60s, no write access). **A fourth narrow exception:** Portfolio Analysis's `GET /api/v1/health/metrics` requires a scoped `X-Metrics-Token` (`PORTFOLIO_METRICS_TOKEN` here, `METRICS_TOKEN` there), set per app via `AppDefinition.metrics_token_setting` and sent to that URL only; it returns dates and counts (`last_transaction_date`, `transactions_total`, `imports_total`) and never dollar amounts, tickers, accounts or P&L, and the dashboard must never hold Portfolio's `APP_TOKEN`. **A fifth narrow exception:** private personal-feed data (news items, sports events, shoe watches/listings, digest runs) lives in `personal_store.py` at `PERSONAL_DB_PATH`; all reads need `DASHBOARD_READ_TOKEN`, watch/state changes need `DASHBOARD_WRITE_TOKEN`, and `POST /internal/daily-digest/send` needs `INTERNAL_REPORT_SECRET`. Sources are an allowlist (RSS feeds; sports = ESPN's public scoreboard JSON via `personal_espn.py`, approved 2026-10-19 as a documented exception; shoe provider unset until approved), only short error codes are stored, and the digest sends once per America/Chicago day (`digest_runs`); the schedule is a manual cron-job.org job, never activated by code. **The Assistant brief** (`personal_assistant.py`, `GET /api/v1/personal/assistant`, read token, `/assistant` page) combines today's Google Calendar events (read-only secret iCal URL, `GOOGLE_CALENDAR_ICS_URL`), project status pushed by `scripts/push_project_status.py` to `/internal/metrics/projects` (folder names, branches, commit subjects, dirty counts and `~/.claude/left-off` notes; joined to GitHub activity by origin slug), priority-team/Top-25/NFL/NBA games, and gym progress from gym_tracker's token-guarded summary (`GYM_TRACKER_URL`/`GYM_TRACKER_TOKEN`). The page reads a stored snapshot of the brief (`assistant_snapshot` in `personal_store`): `POST /internal/personal/refresh` (internal secret, hourly 06:00–24:00 CT via cron-job.org) refreshes news, sports, shoes and own-data, each isolated and reported as a short code, then rebuilds and stores the brief, logging the run to `push_runs` (`personal-refresh`, an Automations row); a GET with nothing stored builds once, and `?force_refresh=true` (the page's Refresh button) rebuilds live. Opening News or Assistant never refreshes upstream; only their Refresh buttons do. The digest still builds its own fresh brief. The digest adds those cards and sends one ntfy summary; `POST /internal/game-reminders/send` (internal secret, every 15 min via cron-job.org) pushes each priority-team game once, within 60 minutes of start. **Daily pushes** (`daily_pushes.py`): `PUSHES` maps kind → (America/Chicago send hour, message builder; `None` = not ready yet); each kind is a Settings toggle stored in `push_prefs` (default off; `GET /api/v1/personal/pushes` read token, `PUT /api/v1/personal/pushes/{kind}` write token), and `POST /internal/daily-pushes/send` (internal secret, hourly via cron-job.org) sends each enabled kind once per Chicago day, marked in `reminders_sent` (`kind:date`) only after ntfy accepts it. **Philosophy** (`personal_philosophy.py`, `/philosophy` page): one entry a day from `app/data/philosophy.json` (60 entries alternating stoic/existentialist, rotated by Chicago date like `learning.py`, no LLM). Quoted passages are verbatim from public-domain translations only (Long, Higginson, Gummere, Common, Garnett, Hollander); Sartre, Camus and de Beauvoir entries are our own paraphrases (`paraphrase: true`) — never add copyrighted translations. The intention/reflection journal (`philosophy_journal`) is private personal data: `GET /api/v1/personal/philosophy/today` and `/journal` need the read token, `PUT /api/v1/personal/philosophy/journal/{date}` the write token. It registers the `philosophy_morning` (7 CT) and `philosophy_evening` (21 CT) daily pushes. **A sixth narrow exception — the NBA daily report** (`personal_nba.py`, `/nba` page): bet_watch pushes one report per slate to `POST /internal/nba-report` (`INTERNAL_REPORT_SECRET`, `kind` must be `nba_daily_report`; contract in bet_watch PR #11), upserted by `slate_date` into `nba_reports` in `personal_store` with 30-day retention, and read back via `GET /api/v1/personal/nba-report?date=` (read token; latest when no date). It holds **picks, prices and percentages only** — never stakes or dollar amounts, bankroll, balances or account data: every payload model forbids extra fields, so a stake/dollar field is a 422, never stored. Spreads are the Watchlist (unproven, tracking only); only moneyline EV > 3% is Targeted, and real money stays gated on targeted CLV ≥ +1% over 200 picks. It registers the `nba_report` daily push (10 CT; `None` until today's report arrives). Otherwise the dashboard holds no Claude, Neon or Fly credentials; the pushing scripts live in `scripts/` (see `scripts/README.md`). Neon is reported as compute hours per project plus the plan (its API has no dollars; on the Free plan the cost is exactly $0 and hours are shown against the per-project allowance). Fly cost per app is an estimate: measured machine run time from Fly's managed Prometheus × published rates, plus volumes and dedicated IPs (Fly has no billing API); a manually entered invoice total is shown beside it, never spread across apps. The financials response folds Fly apps and Neon projects into one row per production registry app (matched by `id`, `fly_app` or `AppDefinition.cost_aliases`); unmatched sources keep their own row.

## Commands

Backend (from `backend/`, Python >=3.11):
```
python -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install -e ".[dev]"
pytest                          # full suite
pytest tests/test_file.py::test_name   # single test
ruff check .                    # lint
uvicorn app.main:app --reload   # run locally, port 8000
```

Frontend (from `frontend/`):
```
npm install
npm run dev      # vite dev server
npm run build    # tsc -b && vite build
npm run lint
npm run test     # vitest run
```

When running the dashboard locally alongside the Vinyl API, start Vinyl API on port 8003 (`uvicorn vinyl_api.main:app --reload --port 8003` from the `vinyl/api` repo) so it doesn't collide with the dashboard's own port 8000.

Set `PROFILE=production` only to check real production endpoints — production never targets localhost.

## Architecture

- `backend/app/registry.py` is the source of truth for monitored targets — **the browser cannot supply arbitrary target URLs**; every profile/service entry the frontend can query comes from this registry.
- **Metrics are opt-in:** only keys in an app's `metric_allowlist` are surfaced (an empty allowlist exposes nothing), and `CheckResult.freshness` is parsed from the allowlisted `data_freshness_at` key. Never allowlist provider quotas or financial/user-level figures (`tests/test_registry.py` guards quotas).
- `backend/app/monitoring.py` performs the actual health checks; `backend/app/incidents.py` + the SQLite file at `INCIDENTS_DB_PATH` (mounted as a Fly volume at `/data` in prod) track incident history; `backend/app/alerts.py` handles push heartbeats/alerting; `backend/app/reports.py` builds surfaced report data; `backend/app/schemas.py` defines the normalized health contract.
- **The health contract distinguishes separate signals**: a monitored service exposes liveness via a `status` field, and may separately expose `provider_status`, `readiness`, or freshness fields — these are never conflated into one flag. The Betting Aggregator's local profile specifically uses `/api/v1/health` for process liveness and `/api/v1/status` for provider/data state; the status endpoint is read-only and must never return odds events, offers, credentials, quotas, or raw provider errors.
- `runbooks/` (bundled into the Docker image at `/app/runbooks`, read via `RUNBOOKS_DIR`) holds per-service incident runbooks (`betting-aggregator.md`, `gym-tracker.md`, `portfolio-analysis.md`, `vinyl.md`) served by the dashboard itself, not just static docs.
- Production registry entries: NFL Confidence, Betting Aggregator, Gym Tracker, Portfolio Analysis and Vinyl are all deployed on Fly.io and monitored. NFL, Betting, Gym and Portfolio are **single-container apps** — one Fly host serves both the UI and the `/api/v1/*` API (`nfl-confidence-web`, `bet-watch`, `aisaac-gym`, `aisaac-portfolio`), so every URL for those apps uses that one host; the old `-web`/`-api` split hostnames no longer exist (`tests/test_registry.py` guards this). Vinyl is still split (`vinyl-catalog` UI + `vinyl-api`). NBA Prediction is push-based (heartbeat only) with no product URL in production — that is intentional, not a bug.
- Fly machines scale to zero, so `monitoring.py` gives each health check a 10s timeout and retries once (connection error, timeout, or 502/503/504) before reporting `down`. A response that needed the retry, or took over ~8s, is reported as `slow` ("waking up") — a non-failing state that never opens an incident. `down` results carry the error in `detail` and the check time in `checked_at`.
- **History and observability:** `health_history.py` stores one row per fresh check (30-day retention, `HEALTH_DB_PATH`); cached responses are never recorded. It powers `GET /api/v1/apps/{id}/health-history`. `GET /api/v1/apps` lists registry apps publicly but includes each app's `stack` map (versions, hosts, databases, from `registry.STACKS`) only for `DASHBOARD_READ_TOKEN` holders. `automations.py` reports last-run/staleness, next expected run, overdue hours and last failure for push jobs (cadences are assumptions used only to flag `stale`); `metrics_store.push_runs` is an append-only 30-day log of each push attempt (time, ok, short error code like `invalid_payload`, never the payload), served by `GET /api/v1/automations/{id}/runs` behind `DASHBOARD_READ_TOKEN`. `GET /api/v1/config-status` returns set/not-set for each secret, never values. History accrues only while the apps are polled (dashboard views or the optional `HEALTH_POLL_INTERVAL_SECONDS` poller).
- **Frontend conventions:** tokens in `frontend/src/theme/theme.css` (light/dark via `[data-theme]`), Iconoir is the only icon set, Motion via `motion/react` with `MotionConfig reducedMotion="user"`. Every list uses the shared `components/primitives/Table` (sortable, searchable, filterable; no zebra stripes or vertical borders). Per-app tabs live in `components/application/`; routes are in `App.tsx`.
- Single-container deploy: the Dockerfile builds the frontend (Node stage) then copies its `dist/` into the Python/uvicorn image alongside `backend/app`; Fly.io (`fly.toml`, app `aisaac-dashboard`) serves it as one process with a persistent volume for the incidents DB.
